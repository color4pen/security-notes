# 相次ぐ国内の不正アクセスに各機関が一斉に注意喚起 ― JPCERT/CCが示した4つの攻撃類型と、国家サイバー統括室・IPAが求める点検

## 要点

### 発表された事実

- JPCERT/CCは2026年10月8日、「直近2026年9月前後」に国内組織で不正アクセスによる個人情報等の漏えい被害が相次いでいるとして注意喚起を公開し、9日に更新した。「技術的な情報の共有が不足しており、把握している情報は限定的かつ断片的」としたうえで、寄せられた情報に基づく4つの攻撃類型と不審な送信元IPアドレスを示した（[JPCERT/CC](https://www.jpcert.or.jp/at/2026/at260030.html)）。
- 4類型は、(A)標的ごとにさまざまな既知の脆弱性を探して悪用を試みるもの、(B)API経由での不正な操作、(C)MetabaseのSQLインジェクションの脆弱性（CVE-2026-72898）、(D)公開Webサーバーからアクセスできるアプリケーションサーバー上へのWebシェル設置（9日に追加）。「すべての事案で同一の攻撃手法が使用されていることを示すものではありません」としている（同）。
- 内閣官房国家サイバー統括室（NCO）は10月9日、大量の個人情報を取り扱う事業者等の情報システムが侵入され、個人情報を含むデータが窃取される事案を「複数確認」しているとして、ウェブシステム等の管理、サプライチェーンを通じた侵害への対策、データの管理の3点で対策の徹底を求めた（[NCO](https://www.cyber.go.jp/pdf/press/taiou.pdf)）。
- IPAは同日、「現段階では、特定のプロダクトやサービスの脆弱性を狙った攻撃とは断定されておらず」、公表事例の傾向から外部公開しているアプリケーションやサービスの侵害、アカウントの侵害が起点になっているとうかがえるとして、経営者に点検と見直しを「至急」実施するよう求めた（[IPA](https://www.ipa.go.jp/security/security-alert/2026/alert20261009.html)）。
- piyologのまとめによると、10月7日に個人情報保護委員会、8日にJPCERT/CCと警察庁、9日にNCO・総務省・経済産業省・IPA・金融庁が、それぞれ注意喚起を公表した（[piyolog](https://piyolog.hatenadiary.jp/entry/2026/10/11/004353)）。

### わかっていないこと

- 一連の漏えい事案が同じ攻撃者・同じ攻撃基盤によるものか（警察庁長官は10月8日、背景や相互の関連性は明らかでないとしたと報じられている）
- JPCERT/CCの4類型が、公表済みのどの事案に当たるか
- ケースDのWebシェルが置かれたアプリケーションサーバーの製品や、設置に使われた手口
- 攻撃にAIが使われているか（セキュリティ企業は振る舞いからの推測にとどまり、直接の痕跡は確認されていないとしている）
- NCOに集約するとされた被害情報や攻撃手法の分析結果が、今後どの程度公開されるか

### 関係しそうな既知の手口

- （考察）ケースBの「アプリを解析してAPIのエンドポイントやキーを特定」「本来画面操作では実行できない内部APIへの攻撃」は、[ローソンID](/security-notes/notes/2026-10-10-lawson-id-app-display-mechanism-2-15m-records/)の「本人に情報を表示する仕組みの悪用」や[skyticket](/security-notes/notes/2026-10-11-skyticket-adventure-three-intrusions-14-64m/)の「管理機能の不正操作」と説明が近い。ただし、各社の事案が注意喚起のどのケースに当たるかは公表されていない。

## 概要

- 9月前後から国内で大量の個人情報漏えいの公表が続いたことを受け、10月7日から9日の3日間で、個人情報保護委員会、JPCERT/CC、警察庁、NCO、総務省、経済産業省、IPA、金融庁が相次いで注意喚起を出した。
- 技術的に最も踏み込んだのはJPCERT/CCで、既知の脆弱性の探索、管理用APIの悪用、Metabaseの脆弱性、Webシェル設置の4類型と、侵害調査に使える送信元IPアドレスやUser-Agentを公開した。
- 共通する一つの脆弱性は見つかっておらず、各機関の求める対策は「外部公開しているものの点検」「APIとアカウントの権限の見直し」「持っているデータを減らす」「ログを見る」に集約される。

> この記事では、公式発表・報道で確認できた内容を「事実」、筆者の推測や意見を「考察」として分けて書いています。確認できなかった情報は書いていません。

**事実（JPCERT/CCの注意喚起）**

- User-Agentの例として、ケースBでは `curl/7.88.1`、`python-requests/2.34.2`、Chrome 126を名乗るMacのブラウザ文字列、ケースCでは `python-requests/2.33.1`、`Metabase-GHSA-vwf4/2.0` を挙げている。ケースB・CのIPアドレスには「調査時点では正規利用されている可能性もあります」との注記がある。
- 被害はスマートフォンアプリなど一般向けのシステムに限らず、BIツールや従業員向け管理システムなど、不特定多数のアクセスを想定していないシステムでも起きているとしている。
- 対策として、APIの単位時間あたりのリクエスト件数の制限、ログイン・パスワードリセット・SMS送信・検索など悪用リスクの高い機能への個別の制限、非公開APIを含む各エンドポイントでのアクセス制御、APIトークンの最小権限と有効期限、漏えいが疑われるトークンの速やかな無効化を挙げる。汎用的な対策として、アクセス元の地域制限、既知の脆弱性の修正、侵害後の横展開対策の見直し、不要な管理機能の公開停止、保存期間を過ぎたデータを残さないことなどを挙げる。

### 国家サイバー統括室（10月9日）

**事実（NCOの文書）**

- 「ウェブシステムに係る脆弱性の悪用、サプライチェーンを通じた侵害、堅牢さを欠くデータ管理など」により、大量の個人情報を扱う事業者等の情報システムが侵入され、個人情報を含むデータが窃取される事案を複数確認しているとした。
- 対策の柱は3つ。(1)ウェブシステム等の適切な管理（脆弱性の管理、多要素認証やアカウント管理、ログの取得・監視などのレジリエンス）、(2)サプライチェーンを通じた侵害への対策（委託先の対策状況の把握、委託契約のセキュリティ要件、委託先への提供情報の最小化と業務終了後のデータ削除、サプライチェーン全体のリスク管理）、(3)データの適切な管理（情報資産の把握、保有情報の最小化、閲覧権限と更新権限の分離、保存データの暗号化、クラウドの保存領域やデータベースの公開設定・アクセス権限の確認、アクセスログの点検）。
- 「必要以上の権限が付与されている場合、不正アクセス時に大量の情報が一度に取得されるおそれがあります」「万が一情報漏えいが発生した場合でも、保有する情報が少なければ被害の拡大を抑えることが可能です」と書いている。
- 経営層に対し、AIの悪用を含む攻撃手法の高度化を挙げて、対策を経営課題と位置づけるよう求めた。被害組織には、技術的な情報をNCOや所管省庁、専門機関等に速やかに共有するよう求めた。

### IPA（10月9日）

**事実（IPAの注意喚起）**

- 速やかに行うべき点検として、自組織が独自に構築・運用している外部公開アプリケーションやサービスの洗い出しと、それぞれの直近のログの確認を挙げた。異常の見分け方はエラーの出力量や平時との差異などで、直近1か月、その後3か月と段階的に範囲を広げ、今後複数回調査する可能性も踏まえて誰がどう調査できるかを把握しておくよう求めている。
- 点検で異常がなくても、外部公開アプリケーションについては公開範囲、認証（多要素認証・パスワード）、アカウントの権限、API連携などアプリケーション構成要素ごとの管理状況、ログの取得内容と保持期間を見直すよう求めた。利用している外部サービス、保有するデータ（保有の是非、保管場所、データアクセスのログ、暗号化）についても見直し項目を挙げている。
- 追記すべき情報があればページを更新するとしている。

### その他の機関（piyologのまとめによる）

**事実（piyologのまとめ）**

- 個人情報保護委員会（10月7日）：注意喚起で技術的安全管理措置を示し、不要な個人データの消去を求めた。資料「WARNING」を改訂し、事例9「APIが悪用される事例」（パラメータの書き換えで他のユーザー情報を取得できた、会員IDが連番だった、アクセス回数の制限がなかったなど）を追加した。
- 警察庁（10月8日）：基本的な対策の再確認と、本人確認を行う事業者に本人確認の徹底を求めた。長官は会見で、事案の背景や相互の関連性は現時点で明らかでないとしたと報じられている。
- 総務省・経済産業省（10月9日）：所管の事業者や業界団体を通じて注意喚起。経済産業省は、被害発生時に提供された情報を事業者の同意なく公表しないとしている。
- 金融庁（10月9日）：運転免許証等の本人確認書類の画像を含む顧客情報が漏えいするインシデントが起きているとして、金融機関等に対策の点検と非対面の本人確認の徹底を求めた。

### セキュリティ企業の分析

**事実（マクニカ、10月7日）**

- 筆者が一連の事件と似た特徴を持つと判断して集計した国内のWebシステムからの個人情報漏えいの公表は、2024年に62件、2025年に84件、2026年は10月6日時点で119件で、うち81件が7月以降だという（[マクニカ](https://security.macnica.co.jp/blog/2026/10/web-incidents2026.html)）。
- 7月以降の81件のうち、公表から原因を読み取れたのは、製品・CMS・プラグイン・分析ツール等の脆弱性9件、認証情報の悪用やパスワード攻撃4件、設定・アクセス制御の不備3件で、65件（80.2%）は分類に必要な説明が不足していたという（同）。
- 事案対応やログ分析からは、特定の脆弱性だけでなくサイトやAPIの不備を広く探る動き、スマートフォンアプリから取り出したAPIキーで正規のアクセスに見える形でAPIを呼ぶケース、必要以上の情報を返すAPI・過剰な権限のAPI・会員向け機能に匿名でアクセスできる問題などが見えているとした。AIによるゼロデイ脆弱性の発見と悪用については「現時点ではそのような状況は確認されていません」としている（同）。

**事実（サイバーセキュリティクラウド、10月9日）**

- マクニカが公開したIPアドレス2件を起点に自社の観測（9月18日〜10月8日、ログの範囲は環境により異なる）を調べたところ、同一とみられる攻撃者が約40分間で326のIPアドレスを使い分け、1,200件を超えるアクセスを複数回行っていたという（[サイバーセキュリティクラウド](https://www.cscloud.co.jp/news/report/202610099351/)）。
- 観測した流れの一例は、SQLインジェクションによる認証回避の探索、事前に作ったとみられるアカウントでのログイン、ログイン後の機能での再探索、ポイント制度のあるサイトでの他人のポイント窃取の探索、一通り試すと引き上げる、というもの。応答を見ながら手を変える動きから、AIエージェントまたはそれに近い仕組みの可能性があるとしつつ、「AIの利用を直接示す痕跡を確認したものではありません」としている（同）。
- 1つのIPアドレスあたりのアクセス数が少ないため、IPアドレスごとのアクセス数やツール特有のパターンに頼る監視では見逃すおそれがあるとし、通常と異なるHTTPレスポンスコードやレスポンスサイズの偏りに注目したログ調査を勧めている（同）。

**考察**

注意喚起を並べて読むと、どの機関も「これを塞げば止まる」という単一の脆弱性を示していない。JPCERT/CC自身が情報は「限定的かつ断片的」と書き、マクニカの集計では7月以降の公表の8割が原因を読み取れない。各社の公表が「不正アクセス」「〇〇件」で止まっていることが、他の組織が自分のシステムを点検するための手がかりを乏しくしている。その中で、JPCERT/CCがIPアドレスやUser-Agent、Webシェルの形を出したことは、ログを遡って調べる材料として意味が大きい。

もう一つ目立つのは、対策の重心が「侵入を防ぐ」から「取られる量を減らす」に寄っていることだ。NCOの「必要以上の権限が付与されている場合、不正アクセス時に大量の情報が一度に取得される」、IPAの「データ保有の是非の再検討」、個人情報保護委員会の不要データの消去は、どれも侵入された後の被害の上限を下げる話である。10月の国内事例の多くが、1つの入口から会員全件に届いていた（[焼肉きんぐ](/security-notes/notes/2026-10-06-yakiniku-king-app-10-7m-members-breach/)のほぼ全会員、[GMOリサーチ＆AI「infoQ」](/security-notes/notes/2026-10-07-gmo-research-infoq-948k-members-point-fraud/)の全件持ち出しなど）ことと合っている。

サイバーセキュリティクラウドの観測にある「ポイント制度のあるサイトで他人のポイントを狙う」動きは、infoQで会員のポイントがAmazonギフトコードに交換された件と似ている。ただし、観測された攻撃者とinfoQの事案が結びつくかはわからない。

## 関係しそうな既知の手口

**事実（既知の知見）**

- OWASP API Security Top 10（2023年版）は、要求したオブジェクトへの権限を確かめない「Broken Object Level Authorization」を1位に、認証の不備や過剰なデータの返却につながる欠陥も上位に挙げている。JPCERT/CCはAPI対策の詳細としてOWASPのガイドラインを参照先に挙げている（[JPCERT/CC](https://www.jpcert.or.jp/at/2026/at260030.html)）。

**考察**

- **ケースBは「アプリは解析される」前提の欠如**：公開しているスマートフォンアプリには、通信先のAPIや、場合によってはAPIキーが入っている。サーバー側が「自社アプリから来た要求だから正しい」と扱っていると、解析した第三者がアプリを通さずに直接APIを呼び、画面ではできない操作（権限の変更や他人のデータの取得）を実行できてしまう。
- **ケースDはJavaアプリケーションサーバーの管理不備でも起きうる**：WARファイルが置かれたという記述から、TomcatなどのJavaアプリケーションサーバーで、外部から届く管理画面やデプロイ機能が使われた可能性がある。設置手口は公表されていないので、既知の脆弱性か、弱い管理パスワードか、別の侵入の後の設置かはわからない。

## 利用者・運用者がいまできること

**事実（各機関の注意喚起に基づく）**

- 自組織が外部に公開しているアプリケーション・サービス・APIを洗い出し、直近1か月、その後3か月と段階的にログを確認する（IPA）。JPCERT/CCが公開した送信元IPアドレスとUser-Agentを侵害調査に使う（JPCERT/CC）。
- APIには単位時間あたりのリクエスト件数の制限をかけ、非公開APIを含む各エンドポイントでアクセス制御を行う。APIトークンは最小権限・適切な有効期限にし、漏えいが疑われるものは無効化する（JPCERT/CC）。
- 業務上必要のない管理機能などのインターネットへの公開を止め、利用地域が限られるならアクセス元の地域を制限する（JPCERT/CC）。
- 利用目的を終えたデータや保存期間を過ぎたデータを残さない（JPCERT/CC、NCO）。委託先に渡した情報も、業務終了後の削除を徹底する（NCO）。
- 被害にあった場合は、技術的な情報をNCO・所管省庁・専門機関に共有する（NCO）。

**考察（運用者向け）**

- ログを見るときは、IPアドレスごとのアクセス数だけでなく、普段と違うレスポンスコード（401・403・404・500番台）の偏りや、同じAPIで返すデータ量の急な変化を見る。サイバーセキュリティクラウドの観測のように、多数のIPアドレスに分散した探索は、IPアドレス単位の閾値では目立たない。
- 自社が配布しているスマートフォンアプリを、自分で解析してみる。埋め込まれたAPIキーや、画面からは呼ばない内部APIのエンドポイントが見えるなら、それは攻撃者にも見えている。
- ログの保持期間を確認する。IPAが3か月まで遡るよう求めている一方、サイバーセキュリティクラウドも環境によってログの範囲が違うと書いている。いま遡れない期間は、後から侵害の有無を確かめる手段がない。

**考察（利用者向け）**

- 流出の公表が続いているので、同じパスワードを複数のサービスで使わない、多要素認証を有効にする、流出元を名乗るメールやSMSのリンクを開かない、という基本が最も効く。

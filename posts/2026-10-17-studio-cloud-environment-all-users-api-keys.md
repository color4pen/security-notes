# Studio ― ノーコードWeb制作基盤のクラウド環境に不正アクセス、全利用者のアカウントとフォーム送信内容・外部APIキーが、復号鍵ごと流出の可能性

## 要点

### 発表された事実

- Studio株式会社は2026年10月16日、同社が利用するクラウド環境に第三者による不正アクセスがあり、預かっている情報が外部に流出した可能性があると公表した（[第一報](https://studio.design/ja/whats-new/unauthorized-access-2026-10)）。
- 第三者がStudioの一部機能の脆弱性を悪用してクラウド環境に不正にアクセスし、環境内のデータを外部から取得できる状態にしていた。この状態は10月14日に同社が対処するまで続いた。実際に取得された事実は確認できていないが、取得されたものとみなして対応している（同）。
- 現時点で確認できている不正アクセスの期間は9月30日〜10月1日（日本時間）。10月13日に社内調査で確認し、13〜14日に脆弱性の修正と経路の遮断を終えた（同）。
- 対象は、Studioに登録しているすべての利用者。アカウント情報（ユーザー名、メールアドレス、ハッシュ化されたパスワードなど）、デザインエディタ・CMSの内容、フォームに送信された内容、Google reCAPTCHA v3の設定情報、Webhook通知のURL、ライブプレビューのURL、API連携に登録された外部サービスのAPIキーやトークン、パスワード保護ページのパスワード、Googleスプレッドシート連携の認証情報、カスタムプロキシ機能のプロキシキーが流出した可能性がある。件数は精査中（同）。
- フォーム送信内容、APIキー・トークン、スプレッドシート連携の認証情報、プロキシキー、reCAPTCHA v3の設定情報、Webhook URLは、暗号化して保存していたものも、復号に必要な鍵が同じ不正アクセスで読み出されたため、内容を知られた可能性がある（同）。
- 2022年12月〜2023年8月に「Studio AI」（当初は「Auto」）の先行利用を申し込んだ人のメールアドレス、ユーザー名、住んでいる国（接続元IPアドレスから判定）も対象。Studioのアカウントを持たない人も含まれる（同）。
- データの改ざんや削除は確認されていない。二次被害の有無は調査中（同）。
- 【2026-10-17追記】Studioで作ったサイトの運営者による公表が続いている。Luupは10月16日、Studio製サイトのフォーム（ポート設置リクエスト、Unimoの問い合わせ、改正道路交通法の質問など4種）から送信された合計21,368件（同じ人の複数回送信を含む）の氏名・連絡先・住所・会社名などが流出した可能性があると発表した。LUUPアプリの登録情報は別システムで対象外（[Luup](https://luup.sc/news/2026-10-16/)）。
- 【2026-10-17追記】ラクスルは10月16日、サービス案内用サイトの問い合わせ・見積もり・資料請求・セミナー申込みなどのフォームに2024年6月3日〜2026年10月15日に入力された6,412件（氏名、所属先組織、電話番号、メールアドレス、相談内容・予算など）が漏えいした可能性があると発表した。印刷通販サイト「ラクスル」の会員・注文・支払い情報は対象外（[ラクスル](https://corp.raksul.com/news/press/261016raksul_studio/)）。
- 【2026-10-17追記】自治体側でも公表が出ている。久留米市文化振興課が事務局を務める「音楽によるまちづくり推進実行委員会」は10月16日、音楽イベント「KURUME MUSIC FES」公式サイトの問い合わせフォームに入力された計75件の氏名・住所・電話番号などが漏えいした可能性があると発表した。サイトの制作にStudioを使っていた（[読売新聞オンライン（Yahoo!ニュース）](https://news.yahoo.co.jp/articles/b056e184fa716a4b70561161f9f79465ffc25567)）。

### わかったこと

- 【2026-10-17】Studio製サイトの運営者側の公表で、フォーム送信内容の件数が出始めた（Luup 21,368件、ラクスル6,412件、【2026-10-17追記】KURUME MUSIC FES 75件）。いずれも、実際に第三者に取得された事実は確認されていないとしている（Luup、ラクスル）。Studio全体の件数は第一報のまま「精査中」。

### わかっていないこと

- 対象となる利用者の範囲と件数
- 悪用された「一部機能の脆弱性」の内容と、それがクラウド環境のデータ取得につながった仕組み
- 9月30日〜10月1日以外に不正アクセスがなかったか、実際にデータが取得されたか
- 暗号化データの復号鍵が、同じ不正アクセスで読み出せる場所にあった理由
- 二次被害（不正ログイン、外部サービスのAPIキーの悪用など）の有無
- 原因の調査結果と再発防止策

### 関係しそうな既知の手口

- （考察）「サービスの一部機能の脆弱性」から「クラウド環境のデータを外部から取れる状態」に進んだ点は、サーバー側に外部URLを取得させるSSRFのような欠陥からクラウドの権限を得る、よく知られた攻撃の流れと矛盾しない。ただし、Studioは脆弱性の種類を公表しておらず、これは推測にすぎない。

## 概要

- Studioのクラウド環境に、一部機能の脆弱性を使った不正アクセスがあり、10月14日の対処まで環境内のデータを外から取れる状態だった。
- 全利用者のアカウントに加え、Studioで作ったサイトのフォームに訪問者が送った内容や、利用者が登録した外部サービスのAPIキーまでが、暗号化を解く鍵ごと読み出された可能性がある。
- 影響はStudioの利用者だけでなく、Studio製サイトのフォームに入力した人や、APIキーを登録した外部サービスにも広がる。

> この記事では、公式発表・報道で確認できた内容を「事実」、筆者の推測や意見を「考察」として分けて書いています。確認できなかった情報は書いていません。

## 発表内容の整理

**事実（Studioの第一報）**

| 項目 | 内容 |

| アカウント情報 | ユーザー名、メールアドレス、ハッシュ化されたパスワードなど |
| Studio上のデータ | デザインエディタ・CMSの内容、フォームに送信された内容、Google reCAPTCHA v3の設定情報、Webhook通知のURL |
| 公開前ページ | ライブプレビューのURL |
| 設定内の認証情報 | API連携（Data Connect API・API連携（Beta））に登録した外部サービスのAPIキー・トークン、パスワード保護ページのパスワード、Googleスプレッドシート連携の認証情報、カスタムプロキシのプロキシキー |

| パスワードの扱い | Studioのパスワードとパスワード保護ページのパスワードはハッシュ化して保存。割り出しは困難だが否定しきれないとして変更を依頼 |
| Studio AI先行申込者 | メールアドレス、ユーザー名、住んでいる国（IPアドレスから判定）。アカウントがない人も含む |

| 同社の対応 | 脆弱性修正と経路遮断。同社システムの決済やログインなどの認証情報は新しいものに切り替え済み、その他も順次無効化・変更中。個人情報保護委員会などへ報告 |
| 今後の公表予定 | 対象範囲と件数、二次被害の調査結果、原因と再発防止策 |

**事実（報道・利用団体）**

- ITmedia NEWSは、Studioのユーザー数を90万人以上（2026年7月の同社発表）と伝えた（[ITmedia NEWS](https://www.itmedia.co.jp/news/article/2610/16/2000002332/)）。
- 埼玉県は10月16日、「さいたま緑の森博物館」がイベント申込や問い合わせの受付に使っていた外部サービス（Studio）で不正アクセスがあり、同館が取得した個人情報計162件について漏えいの可能性を否定できないと公表した（[埼玉県](https://www.pref.saitama.lg.jp/a0508/news/page/news2026101603.html)）。

**考察**

この件の重さは、Studioが「Webサイトを作る道具」であると同時に、作ったサイトの「お問い合わせフォームの受け皿」でもあった点にある。漏れた可能性があるのはStudioの利用者（サイトの制作者・運営者）の情報だけではない。そのサイトのフォームに名前や連絡先、相談内容を入力した訪問者の情報も含まれる。訪問者は自分がStudioを使っていたとは知らないので、知らせる役目は各サイトの運営者に回ってくる。埼玉県のような公表は、今後もしばらく続くと思われる（考察）。

もう1つは「暗号化していたのに読まれた」理由だ。Studioは、暗号化したデータと、それを解く鍵が、同じ不正アクセスで読み出されたと説明している。保存時の暗号化は、ディスクやバックアップが単体で盗まれたときには効く。しかし、アプリと同じ権限で鍵まで取れる状態になると、守りにならない。どの権限で何が読めたのかは、原因の続報を待つ必要がある（考察）。

- Luupは、Studio上で受け付けていたフォームをすべて停止し、外部サービスを使った個人情報取得の方法を見直すとしている。ラクスルは、自社サイトや関連システムへの不正アクセスは確認されていないとしている。

**考察（2026-10-17追記）**

Luupの対象には、現在はStudio以外のシステムで運用しているフォーム（ポート設置リクエストなど）の、過去の送信内容も含まれる（Luupの発表）。フォームの運用をやめても、過去の送信内容がStudio側に残っていたことになる（考察）。Studioのフォームを使っていた運営者は、現在使っているフォームだけでなく、過去に使っていたフォームの送信データがStudio上に残っていないかも確認する必要がある。

## 関係しそうな既知の手口

**事実（既知の知見・同種事例）**

- JPCERT/CCは10月15日、相次ぐ国内の不正アクセスに関連して攻撃元サーバーを調べた結果を公表した。攻撃者がAIを使って既知の脆弱性のスキャンやAPI経由の攻撃をしていたこと、アプリを解析して見つけたAPIにSSRF（サーバーに外部URLへリクエストを送らせる脆弱性）がないかを調べていた痕跡があったことを報告し、外部URLを取得するAPIではアクセス先とリダイレクト後の宛先を検証するよう勧めている（[JPCERT/CC Eyes](https://blogs.jpcert.or.jp/ja/2026/10/web_api_attacks.html)）。
- コミューンでは、全コミュニティ共通のログイン用署名鍵が奪われ、1つの秘密で多くの企業のコミュニティの管理者になりすませた（[記事](/security-notes/notes/2026-10-10-commune-community-platform-signing-key-307k-members/)）。

**考察**

- **本件とSSRFを結びつける根拠は、まだない**：Studioが公表したのは「一部機能の脆弱性」と「クラウド環境のデータを外部から取得できる状態」までで、脆弱性の種類も、JPCERT/CCが調べた攻撃者との関係も書かれていない。ただ、外部URLを扱う機能（Webhook、API連携、カスタムプロキシなど）を持つサービスでは、サーバーにクラウドの内部向けアドレスを取りに行かせ、クラウドの権限を得るのが典型的な攻撃の流れで、確認する価値はある。
- **「1つの鍵ですべての利用者分が開く」設計**：コミューンの署名鍵と同じように、全利用者のデータを1つの鍵（または同じ権限で取れる鍵）で暗号化していると、その鍵が1回漏れるだけで全員分が読まれる。利用者ごとに鍵を分け、鍵は専用の鍵管理サービスに置いて、アプリの権限では取り出せないようにする設計が考えられる。

## 利用者・運用者がいまできること

**事実（発表に基づく）**

- メールアドレスとパスワードでログインしている人は、Studioのパスワードを変える。同じパスワードを他で使っていれば、そちらも変える。GoogleやFacebookのログインだけを使っている人は不要（第一報）。
- ライブプレビューのURLを発行していれば削除し、必要なら新しいURLを発行する（同）。
- 該当機能の利用者には個別メールで案内している。API連携のキーの切り替え、パスワード保護ページのパスワード変更、フォーム送信者への連絡、スプレッドシート連携の解除、プロキシキーの切り替え、Webhook URLの切り替え（同）。
- Studioを装ったフィッシングに注意する。同社がメールや電話でパスワードや認証情報を尋ねることはない（同）。

**考察（Studioでサイトを運営している側）**

- API連携に登録していた外部サービスのキーは、「Studio側で切り替える」だけでなく、外部サービスの管理画面で古いキーを無効にする。そのうえで、9月30日以降にそのキーで想定外の利用がなかったか、外部サービス側のログを確認する。
- Googleスプレッドシート連携を解除したら、Googleアカウントの「サードパーティのアクセス」でもStudioへの許可が外れているか確認する。
- フォームで個人情報を受け付けていた場合、送信者への知らせ方と、個人情報保護委員会への報告が必要かを、自社の個人情報の担当とすぐに相談する。

**考察（SaaSを運営する側）**

- 外部URLを取得する機能（Webhook、プロキシ、URLからの読み込みなど）は、クラウドのメタデータ用アドレスや社内向けアドレスに届かないようにし、リダイレクト後の宛先も検証する。
- 利用者のデータを暗号化する鍵は、アプリの実行権限だけでは丸ごと取り出せない場所に置く。
